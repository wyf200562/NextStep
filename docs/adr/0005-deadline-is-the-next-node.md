# Deadline 即下一个节点，一个申请只有一个时刻指针

求职没有可预期的终局时刻，用户永远只知道「下一件事是什么时候」，而且这个时刻多由邮件、社交软件或招聘软件告知，抓不到、推不出来。所以 `Application` 上只保留一个可空时刻 `deadline`，它本身就是「下一个节点」：面试来临时用户把它改成面试时间，节点过去后改成下一个。`InterviewRound.scheduledAt` 保留为那场面试的历史记录与排序依据，但退出「即将到来」的计算；保存轮次时若 `deadline` 为空或轮次时间更早，则把该时刻写入 `deadline`。`ApplicationNextNode` 与它的 `Kind` 枚举因此删除——「下一个节点」不再是一个要求和的派生值，而是字段本身。

## Considered Options

- **保留两个源，派生出下一个节点**（即被删掉的 `ApplicationNextNode`）。被否：派生结论无法落库（ADR-0002），三个消费者各自实现边界，已经给出互相矛盾的答案。
- **建统一的节点表**（`deadline` 与面试时刻合成 milestone 集合）。被否：要动 SchemaV1 迁移，且 `InterviewRound` 的 format/result/contact 在通用节点表里退化成一堆空字段；换来的「一个申请可以并存多个待处理节点」不是当前需求。
- **保留两个源，但把边界在接口上分成两个查询**。被否：仍然要维持两份时间的一致性，只是把矛盾起了名字。

## Consequences

- 只有一个指针，所以一个申请同时只能表达一个待处理节点。想同时记「OA 截止」和「offer 回复截止」做不到，必须等前一个过去再推进。
- 指针由人推进，会过期。过期是可见状态（列表标「已过」、概览报数），不是静默错误；这也是取消存量数据迁移的前提。
- 同一时刻可能在轮次和 `deadline` 上各存一份。这份重复是有意的，换来「接下来」只有一个来源；不做自动对账，两边不一致时以 `deadline` 为准。
- 「接下来 7 天」的下界按时刻（`>= now`）、上界按天（今天 +8 天 00:00）。两个锚点不同是有意的：一个回答「哪些还没过去」，一个回答「数到第几天」。
